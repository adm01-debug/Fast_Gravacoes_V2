## Contexto

Auditoria histórica (sessions anteriores) identificou que a política RLS de `password_reset_requests` estava configurada com `TO authenticated`, bloqueando usuários não autenticados (`anon`) de submeter solicitações de redefinição de senha. Nenhum usuário que esqueceu a senha conseguia recuperar acesso.

Origem do achado: `analise-prs/auditorias-anteriores.md` — situação CONFIRMADO E PENDENTE.

## Arquivo alterado

`supabase/migrations/20261031184500_fix_password_reset_anon_policy.sql`

### Conteúdo da migration

```sql
-- Remove as 3 variantes históricas de política (se existirem)
DROP POLICY IF EXISTS "Allow insert for all users" ON password_reset_requests;
DROP POLICY IF EXISTS "Allow users to insert their own reset requests" ON password_reset_requests;
DROP POLICY IF EXISTS "allow_authenticated_insert" ON password_reset_requests;

-- Cria política correta: anon e authenticated podem inserir com status = 'pending'
CREATE POLICY "allow_anon_authenticated_insert"
  ON password_reset_requests
  FOR INSERT
  TO anon, authenticated
  WITH CHECK (status = 'pending');
```

## Análise de segurança

- O `WITH CHECK (status = 'pending')` impede inserção de registros com status arbitrário — correto.
- Não amplia acesso além do necessário: `anon` pode apenas inserir (não SELECT/UPDATE/DELETE).
- As políticas removidas são variantes históricas da mesma política; o DROP é necessário para eliminar duplicação.
- Não há dados sensíveis expostos.
